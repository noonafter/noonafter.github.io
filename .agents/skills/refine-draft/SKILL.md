# 精炼技术博客草稿

此技能仅适用于当前仓库 `D:\\alc\\blog\\noonafter.github.io`。默认从 `draft/` 读取素材，将生成物保存到 `draft/refined/`，不直接发布到 `_posts/`。

## 阶段 1：定位素材

- 用户给出文件时读取指定文件；给出目录时读取目录及子目录中的 `.md` 文件。
- 未给出位置时，先列出 `draft/` 中的候选文件并说明选择依据。
- 汇总素材清单，识别图片、代码文件和可能属于同一主题的多份笔记。

## 阶段 2：内容审查

检查技术定义、代码/API 用法、版本信息、因果关系和推导过程。区分“原文明确给出”“可由上下文推断”和“需要外部验证”的内容。发现错误、缺失或过时信息时，列出问题、依据和修正建议；不要把未经验证的补充写成事实。

## 阶段 3：规划

判断单篇还是系列：单篇聚焦一个核心问题；主题独立、篇幅明显超过约 6000 字或包含清晰技术层次时考虑拆分；过短内容优先合并或补充必要背景。为每篇给出标题、二级/三级大纲、删减项和补充项。

规划完成后必须停下来，请用户确认文章划分和大纲，再生成正文。用户未确认时不得写入最终草稿文件。

## 阶段 4：生成草稿

用户确认后，按基础概念到实践应用的顺序逐篇生成。每篇生成后等待用户审阅，再继续下一篇。文件保存为 `draft/refined/post{编号}_{topic_keywords}.md`：编号从 1 开始，关键词使用 2-4 个小写英文单词和下划线。

正文规范：

- 第一行直接是 `# 博客主标题`，不添加寒暄、开场白、结语或过程说明。
- 使用 H2/H3（必要时 H4）组织连续的知识层次，推荐“概念定义 → 底层原理 → 代码示例 → 最佳实践/注意事项”。
- 使用直接、简洁的书面技术语言和短句。禁止口语化表达、比喻、拟人、情绪化修辞和无实义的强调词。
- 用 **加粗** 标注核心概念或重要结论；对比使用表格；代码块必须带语言标识；术语、API 和变量名使用行内代码。
- 保留技术深度、必要推导、限制条件和场景差异。不得虚构事实、测试结果、链接或代码行为。
- 文章之间确有依赖关系时使用已确认文件名的相对链接 `./YYYY-MM-DD-title.md`；不要链接到不存在的文件。

## 交付检查

检查标题层级、Markdown 语法、代码块语言、链接、事实一致性和字数是否符合规划。报告生成文件、路径、约数和主要章节。此技能只生成草稿；发布动作交由 `publish-post` 技能处理。
