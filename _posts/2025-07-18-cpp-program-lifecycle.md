在 IDE 中开发 C/C++ 程序，一定会执行“构建”和“运行”这两个操作。但从源文件到进程退出，中间还经过了操作系统装载、动态链接和运行时初始化等环节。

本文按 **构建、装载、运行、退出** 四个阶段组织这条链路。目标不是展开每个阶段的全部实现细节，而是明确它们各自解决什么问题、何时交接控制权，以及调试时应到哪里观察问题。

## 一、四个阶段与责任边界

可以将一个常规 Linux C/C++ 程序的生命周期概括为：

```text
源文件
  -> 构建
可执行文件或共享库
  -> 装载
可运行的进程映像，完成运行时初始化
  -> 运行
main 及其创建的线程执行应用逻辑
  -> 退出
运行时清理，内核回收进程资源
```

这四个阶段的主要责任不同：

| 阶段 | 主要参与者 | 关键结果 |
|---|---|---|
| 构建 | 编译器、汇编器、链接器、构建系统 | 产生 ELF 可执行文件或共享库，并记录运行所需元数据 |
| 装载 | 发起执行请求的进程（如 shell 或 IDE）、内核、动态链接器、CRT 启动代码（包括 `_start` 等） | 建立进程映像，处理依赖和初始化，将控制权交给 `main` |
| 运行 | 应用代码、线程库、系统调用接口 | 执行业务逻辑，申请和释放运行期资源 |
| 退出 | CRT 退出处理（包括 `exit` 等）、内核、父进程 | 处理用户态清理，释放内核资源，传递退出状态 |

这里的“CRT 启动代码”指 `_start` 及其调用的 C 库启动逻辑；它负责在 `main` 前交接参数并执行必要初始化。“CRT 退出处理”指正常退出时由 `exit` 等路径触发的清理逻辑，可以理解为一系列的清理操作。

IDE 的“运行”按钮并不只做一次函数调用。它可能按运行配置先触发构建，再由 IDE 或其启动的辅助进程创建目标进程并执行目标文件。终端中运行 `./app` 不会构建程序；该命令只由 shell 请求执行已经生成的目标文件，随后进入相同的装载、运行和退出流程。

## 二、构建：把源码变成可装载映像

构建的主线是：

```text
源文件
  -> 预处理
  -> 编译
  -> 汇编
  -> 链接
ELF 可执行文件或共享库
```

这里的“链接”指的是构建阶段由静态链接器 `ld` 参与完成的链接。对于需要进行动态链接的程序，`ld` 会完成构建期能够完成的链接工作，并将共享库依赖、动态符号和重定位等信息写入 ELF 文件；程序装载时，再由动态链接器（如 `ld-linux`）加载依赖库并完成动态链接。

关于构建中各个阶段具体职责，可参考 [C/C++构建过程基础](./2025-01-07-c-cpp-compile.md)，静态链接与动态链接的分工，参考 [链接与库](./2025-02-02-c-cpp-link.md)。本文只保留与后续阶段有关的结论：**链接完成后得到的是一个可供系统装载的文件，不是已经在执行的进程。**

ELF 同时保存两类信息：

- 面向链接的节，例如 `.text`、`.data`、`.bss` 和符号表；
- 面向装载的程序段，例如可装载段 `PT_LOAD`、动态链接信息和动态链接器路径。

调试运行问题时，应区分这两个视角。节描述链接器如何组织内容；内核装载时主要依据程序段建立映射，而不是逐个依据 `.text`、`.data`、`.bss` 建立固定的运行时区域。

可以将构建阶段理解为：链接器把已知的初始数据和“启动时仍要执行的初始化步骤”写入 ELF，但不会在构建时实际运行程序。以全局对象为例：

```cpp
int retry_limit = 3;                       // 初始值在构建时已经确定
int error_count;                           // 初始值为 0
std::string banner = make_banner();        // 需要执行函数和构造函数
```

- `retry_limit` 的初始值 `3` 会作为数据写入程序映像，通常位于 `.data`；
- `error_count` 的初始值为 `0`，通常由 `.bss` 表示。文件不需要保存一串零字节，装载时系统会保证读取该对象时得到零值；
- `banner` 必须调用 `make_banner()` 并构造 `std::string` 对象。链接器只会把所需代码和初始化入口写入 ELF，不会在构建机器上调用它们；程序装载后，C++ 启动代码会在进入 `main` 前完成这类初始化。

`banner` 不宜简单归入 `.data`；`std::string` 的构造还可能申请堆内存。这里关注的是它需要在装载阶段执行构造函数。

因此，构建完成时，程序文件已经保存了 `retry_limit` 的初始值，并记录了 `error_count` 所需的空间和零初始化语义，但 `banner` 对象还没有实际构造。C++ 初始化规则见 [C++ 初始化详解](./2024-04-16-cpp-initialization-semantics.md)。



## 三、装载：从文件到 `main`

装载阶段回答的问题是：一个磁盘文件如何成为可以被 CPU 执行的进程。

### 1. 发起执行请求的进程

shell 常见的做法是通过 `fork` 创建子进程，再由子进程调用 `execve` 执行目标程序。IDE、服务管理器和其他进程启动 API 的具体实现可以不同，因此 **`fork` 不是所有程序启动都必须经过的步骤**。

真正将目标程序映像装入当前进程的是 `execve`。调用成功后，进程通常保持原有 PID，但旧的用户态程序映像被新映像替换。`fork` 的资源继承和写时复制机制属于另一条专题，见 [fork原理解析：从深浅拷贝的角度](./2025-02-09-linux-process.md)。

### 2. 内核建立进程映像

内核解析 ELF 的程序头，建立新的用户态地址空间，并准备初始栈、参数、环境变量和辅助向量等内容。可装载程序段形成相应的虚拟内存映射，堆的起点、栈和其他辅助区域也在此阶段具备位置。

这里的关键是 **虚拟映射已经建立，不代表所有程序内容已经进入物理内存**。文件映射页和匿名页通常在首次访问时才需要实际物理页；`.bss` 不保存大量零字节，其初始零值由装载和虚拟内存规则保证。缺页、页表和文件页缓存的关系见 [虚拟地址空间分类与处理](./2025-10-20-virtual-memory.md)。

### 3. 动态链接器和语言运行时完成接力

对于动态链接的 ELF，内核会根据 `PT_INTERP` 指定的路径装载动态链接器。ELF 规范将这个字段称为 program interpreter，但这里指的是 `ld-linux` 一类的动态链接器，不是脚本语言解释器。此时，控制权先交给动态链接器，而不是直接进入应用的 `main`。

动态链接器负责装入所需共享库、处理符号重定位，并执行共享库所需的初始化。之后，控制权到达主程序的入口 `_start`。C 运行时从初始栈取得 `argc`、`argv` 等信息，执行主程序的初始化函数；C++ 的非局部对象若需要动态初始化，也在这一阶段完成。最后才调用 `main`。

```text
execve
  -> 内核建立新映像
  -> 动态链接器处理依赖和重定位
  -> _start
  -> C/C++ 运行时初始化
  -> main
```

这也是“构建成功但点击运行失败”常常发生在 `main` 之前的原因。缺少共享库、库路径配置不正确或初始化代码失败，都可能阻止程序进入应用逻辑。动态库路径、`RPATH`、`RUNPATH` 和 `LD_LIBRARY_PATH` 的专题说明见 [Linux 动态库链接机制：编译期与运行期的分离](./2026-01-06-linux-dynamic-linking.md)。

## 四、运行：`main` 之后的应用执行

本文将 **进入 `main` 视为装载完成、应用运行开始的边界**。这不是说装载阶段之后不再发生内存映射、动态符号绑定或库加载，而是为了在调试时明确区分两类问题：

- `main` 之前失败，优先检查可执行文件、共享库依赖、运行环境和初始化代码；
- `main` 之后失败，优先检查应用控制流、线程、资源管理和输入输出。

运行期间，应用可以创建线程、请求堆内存、打开文件和套接字，并通过系统调用向内核申请服务。程序也可以通过 `dlopen` 在运行中再加载共享库，因此“装载完成”不表示后续不会出现动态装载行为；它只表示启动所必需的初始化已经将控制权交给了应用入口。

函数内局部静态对象也不属于启动阶段的全局初始化。它在程序第一次执行到定义处时才完成初始化。将这类延迟初始化与非局部对象初始化区分开，能够避免把问题错误归因于启动顺序。

## 五、退出：用户态收尾与内核回收

程序退出并不等于 `main` 的最后一条语句执行完毕。退出至少包含两层工作：运行时处理用户态清理，内核回收进程持有的系统资源。

### 1. 正常退出

从 `main` 返回通常等价于以该返回值调用 `std::exit`。显式调用 `exit` 也走正常退出路径。运行时会执行已注册的退出处理函数和静态存储期对象的析构等清理工作；C 标准 I/O 缓冲也会在相应的正常退出处理中收尾。

这与函数局部对象的析构不同。局部对象在作用域结束或 C++ 异常栈展开时析构；静态存储期对象的析构则属于进程正常退出时的清理。RAII 与异常栈展开的关系可参考 [RAII 与智能指针的内部机制](./2025-04-07-raii-smart-pointer.md)。

### 2. 立即退出和信号终止

`_exit` 或 `_Exit` 直接进入内核终止路径，跳过常规用户态退出处理。因此它适合不应继续执行用户态清理代码的受限场景，不应作为普通业务流程的默认选择。

另一类退出来自信号。例如，非法内存访问可能使内核向进程发送 `SIGSEGV`，`abort()` 通常导致 `SIGABRT`。信号可以有自定义处理方式；在默认动作下，部分信号会终止进程，并可能生成 core 文件。

**Unix 信号与 C++ 异常不是同一套机制。** C++ 的 `throw` 由语言运行时进行匹配和栈展开；未捕获异常通常会进入 `std::terminate`。硬件或内核事件则可能转换为 POSIX 信号。调试崩溃时，先区分这两类路径，才能选择正确的工具和修复位置。

### 3. 内核结束进程

无论通过何种用户态路径结束，内核最终都会释放进程地址空间、关闭或释放文件描述符引用，并回收其他内核资源。进程会保留退出状态等少量信息，进入僵尸状态；父进程调用 `wait` 或 `waitpid` 获取该状态后，进程才完成最终回收。

因此，完整的退出链路是：

```text
main 返回 / exit / _exit / 信号终止
  -> 可选的用户态清理
  -> 内核释放进程资源
  -> 父进程 wait 获取退出状态
```

## 六、用工具定位所处阶段

调试时不必一次理解所有细节。先判断问题位于哪个阶段，再选对应工具即可。

| 观察目标 | 示例命令 | 可回答的问题 |
|---|---|---|
| 构建产物类型和程序段 | `readelf -h -l ./app` | 文件是否是目标平台可执行 ELF，装载器将依据哪些程序段工作 |
| 动态依赖和嵌入路径 | `readelf -d ./app` | 程序需要哪些共享库，是否记录了 `RPATH` 或 `RUNPATH` |
| 运行时内存映射 | `cat /proc/<pid>/maps` | 可执行文件、共享库、堆和栈在进程中如何映射 |
| 系统调用边界 | `strace ./app` | 是否已执行 `execve`，在哪个文件、库或系统调用附近失败 |
| 退出状态 | `echo $?` | shell 观察到的程序退出结果 |

这些命令只用于建立阶段位置感。发现具体问题后，再进入编译、链接、虚拟内存、进程或调试器等对应专题。

## 七、把四个阶段连成一条调试主线

面对“程序为什么不能运行”或“退出为什么不符合预期”这类问题，可以按以下顺序定位：

1. **构建**：产物是否生成，目标架构、链接依赖和编译选项是否正确。
2. **装载**：`execve` 后是否能找到动态链接器和所需共享库，初始化是否在 `main` 前失败。
3. **运行**：是否已经进入 `main`，问题发生在线程、内存、I/O、业务逻辑还是运行中动态加载。
4. **退出**：属于正常退出、立即退出、未捕获异常还是信号终止；父进程是否正确收集退出状态。

这条链路的重点不是把所有机制放在同一层讨论，而是为每个机制建立准确的位置：**构建负责生成映像，装载负责建立并初始化进程，运行负责执行业务，退出负责结束并回收资源。**
