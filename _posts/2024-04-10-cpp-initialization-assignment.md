## 一、初始化与赋值的本质区别

**初始化**发生在对象生命周期开始时，建立对象及其初始状态；**赋值**发生在对象已经存在时，由赋值运算符替换其值。两者是否产生额外开销，取决于类型、重载和优化结果，不能用固定的汇编形式概括。

### 1、为什么应在初始化阶段建立状态

引用和 `const` 对象必须在初始化时确定状态，不能通过后续赋值补上：

```cpp
int x = 10;
// int& r;       // 错误：引用必须初始化
const int limit = 10;
```

对类成员，构造函数初始化列表直接选择成员构造方式；在构造函数体内写赋值时，成员已经按其默认初始化规则建立，随后才调用 `operator=`。这可能引入不必要的默认构造和资源替换，但具体成本取决于类型实现。

| 特性 | 初始化 | 赋值 |
|------|--------|------|
| 发生时刻 | 对象生命周期开始时 | 对象已存在之后 |
| 主要接口 | 构造函数 | 赋值运算符 `operator=` |
| `const`/引用 | 可在初始化时建立 | 通常不能重新绑定或修改 |
| 资源处理 | 由构造函数建立资源状态 | 由赋值运算符决定如何处理旧状态 |

## 二、构造函数初始化列表

```cpp
class MyClass {
    int x;
public:
    MyClass() : x(5) {} // x 直接以 5 初始化
};
```

成员的实际初始化顺序由声明顺序决定，而不是初始化列表中的书写顺序。使用初始化列表也适用于不可默认构造、引用和 `const` 成员。

## 三、底层视角：对象状态的前提

构造函数接收的是尚未成为该类型对象的存储空间，并负责建立不变量。赋值运算符接收的是已经构造完成的对象，因此可以读取并处理旧状态。赋值是否先释放资源、是否复用容量、是否采用 copy-and-swap，都由具体类型的实现决定。

下面的代码只说明一种资源管理策略，不能代表所有类：

```cpp
MyClass& operator=(MyClass other) {
    swap(*this, other);
    return *this;
}
```

传值参数先构造副本，交换成功后由副本析构旧资源。若副本构造失败，原对象通常保持不变；这正是 copy-and-swap 常见的异常安全性质。

### 1、汇编示例（示意）

对于简单标量，初始化和赋值都可能编译为 `mov`；对于类类型，可能包含构造、析构、分配和拷贝。以下伪汇编仅用于说明调用边界，实际指令取决于类型、编译器、ABI 和优化级别：

```asm
# 示意：初始化对象
call MyClass::Constructor

# 示意：给已存在对象赋值
call MyClass::operator=
```

## 四、对象生命周期与异常安全

对象只有在其初始化过程完成后，才能按该类型使用。若构造函数或某个成员构造函数抛出异常，已经构造完成的成员会按相反顺序析构，存储空间随后释放；目标对象不会进入可用状态。

这条生命周期规则不表示构造期间不存在任何访问：构造函数可以访问已完成初始化的基类和成员，也可以通过受限方式使用 `this`。将对象发布给其他线程则需要额外的同步，不能仅依赖构造顺序。

## 五、赋值的异常安全

赋值运算符可能采用直接修改、资源复用或 copy-and-swap 等策略。不能假定所有类都执行“释放旧资源后再分配新资源”，也不能假定失败后都保留原值；应以类型的赋值运算符契约为准。实现自定义资源类型时，应明确基本、强或不抛出异常保证。

## 六、多线程环境下的可见性

初始化和赋值默认都不是跨线程的原子同步操作。一个线程写入对象、另一个线程无同步读取，可能产生数据竞争；即使底层恰好使用单条指令，也不能据此获得 C++ 内存模型保证。

需要共享简单值时可使用 `std::atomic<T>`；共享类对象通常使用互斥量或其他同步协议。`acquire`/`release` 等内存序建立的是可见性与排序关系，具体硬件指令由实现决定。

## 七、实践建议

- 在构造函数初始化列表中直接初始化成员，尤其是引用、`const` 和不可默认构造成员。
- 先确定类型的资源和异常安全契约，再选择赋值实现策略。
- 将汇编视为特定编译配置下的观察结果，不能用它替代语言层面的对象模型。
- 跨线程发布对象时使用 `std::atomic`、互斥量或其他明确的同步机制。
