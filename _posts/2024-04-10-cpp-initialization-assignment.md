## 一、先区分初始化与赋值

初始化建立对象的第一个有效状态，赋值修改已经存在对象的状态。两者的差别不是“是否把一个值写入内存”，而是**操作开始时目标对象是否已经成立**。

| 对比项 | 初始化 | 赋值 |
|------|--------|------|
| 目标状态 | 存储空间尚未成为目标类型对象 | 已完成构造、可以读取旧状态的对象 |
| 主要接口 | 构造函数、复制构造函数、移动构造函数 | `operator=` |
| 资源处理 | 建立资源所有权和类不变量 | 决定如何处理旧资源并接收新值 |
| 典型限制 | 引用、`const` 和不可默认构造成员必须在此阶段确定 | 通常不能重新绑定引用或修改 `const` 成员 |

```cpp
std::string first{"Ada"}; // 初始化：建立一个新对象
first = "Grace";          // 赋值：修改已经存在的对象
```

对基础类型，这两种操作可能都只需要一条机器指令；对拥有资源的类，初始化和赋值通常会经过不同的函数和资源路径。最终代码仍取决于类型、编译器和优化级别。

## 二、构造阶段：从存储空间到合法对象

### 1、成员初始化列表决定构造方式

构造函数体执行前，基类和成员已经按照初始化规则完成构造。初始化列表选择它们使用的构造函数；如果成员没有出现在列表中，则使用类内初始值或默认初始化。

```cpp
class Account {
    std::string owner;
    const int id;
public:
    Account(std::string name, int value)
        : owner(std::move(name)), id(value) {}
};
```

成员的实际初始化顺序始终是：**基类、按声明顺序排列的非静态数据成员，最后进入构造函数体**。初始化列表中的书写顺序不会改变这一规则；应按成员声明顺序书写，避免误读和编译器警告。

### 2、在构造函数体内赋值不是成员初始化

```cpp
class Config {
    std::string path;
public:
    Config(const char* value) {
        path = value; // path 已默认构造，这里调用赋值运算符
    }
};
```

对于 `std::string` 等类成员，上述写法先默认构造成员，再在构造函数体内赋值。初始化列表则可以直接调用目标构造函数。是否产生可观测的额外开销取决于类型实现，但语义上的两阶段过程是不同的。

## 三、复制、移动与赋值的关系

初始化一个新对象时，源对象的值类别决定可能调用的构造函数；给已有对象赋值时，调用的是赋值运算符：

```cpp
std::string source{"text"};
std::string copy{source};            // 复制构造
std::string moved{std::move(source)}; // 移动构造

copy = moved;                        // 复制赋值
copy = std::move(moved);              // 移动赋值
```

复制通常需要建立独立资源，移动则可以转移资源所有权，但移动后的源对象仍然是有效对象，只保证满足类型规定的可用状态。不能把移动简单理解为“复制几个指针”；具体成员和资源由类的移动构造函数、移动赋值运算符定义。

如果类声明了析构函数、复制操作或移动操作中的一部分，编译器生成其余特殊成员函数的条件会受到影响。资源管理类应明确遵循[规则五](https://en.cppreference.com/w/cpp/language/rule_of_three)或使用标准库资源类型，避免隐式复制导致重复释放。

## 四、赋值运算符如何处理旧状态

赋值运算符的前提是 `*this` 已经是合法对象，因此实现必须处理旧状态、自我赋值和新值准备。不同类型可以采用不同策略：

1. **直接修改**：逐个更新成员，适合不会抛出异常或有明确基本保证的类型。
2. **资源复用**：保留已有容量或句柄，减少重新分配。
3. **copy-and-swap**：先准备副本，再交换资源，使失败发生在修改当前对象之前。

```cpp
class Buffer {
public:
    Buffer& operator=(Buffer other) {
        swap(*this, other);
        return *this;
    }

    friend void swap(Buffer& left, Buffer& right) noexcept;
};
```

传值参数会先完成复制或移动构造；`swap` 成功后，形参析构并释放原对象资源。若副本构造失败，当前对象尚未被修改，因此这种实现通常可以提供强异常安全保证。它并非所有类型的最佳选择，是否适用取决于交换操作、分配成本和类型不变量。

## 五、异常安全与对象生命周期

### 1、构造失败时对象不会成立

如果基类、成员或构造函数体抛出异常，已经完成构造的子对象会按相反顺序析构，尚未完成的部分不会被析构，外层存储随后释放。目标对象不会进入可用状态，也不能对它执行普通成员访问。

构造函数内部可以访问已经构造完成的基类和成员，也可以在受限条件下使用 `this`；但在构造完成前把 `this` 发布到外部，会使外部代码观察到不完整对象，通常是错误的设计。

### 2、赋值失败时取决于赋值契约

赋值运算符可能提供三种常见保证：

| 保证 | 失败后的状态 |
|------|--------------|
| 基本保证 | 对象仍合法，但值可能已改变 |
| 强保证 | 操作失败时对象保持原值 |
| 不抛出保证 | 操作不会抛出异常，常用于 `swap` 和移动操作 |

不能假定所有赋值都先释放旧资源，也不能假定所有失败都会保留原值。调用者应依据类型文档选择策略；自定义资源类型则应在接口设计中明确保证级别。

## 六、底层代码与汇编的边界

初始化和赋值在机器层面可能共享部分指令，但它们在语言层面的前提不同。下面的伪汇编只表示可能的调用边界：

```asm
# 示意：在原始存储空间中建立对象
call Account::Account

# 示意：对已存在对象执行赋值
call Account::operator=
```

对于标量，优化器可能消除临时对象或合并读写；对于类类型，可能出现构造、析构、资源分配和异常路径。汇编结果必须结合具体类型、ABI、编译器版本和优化选项分析，不能用一段示意代码推导通用性能结论。

## 七、跨线程使用对象

初始化和赋值默认都不是跨线程的同步操作。一个线程写入对象、另一个线程无同步读取，会产生数据竞争；即使某个平台把一次对齐的标量写入实现为单条指令，也不等于满足 C++ 内存模型。

发布已经构造完成的对象时，需要使用互斥量、线程安全队列或带有适当内存序的原子变量建立同步关系。`std::atomic<T>` 只适用于满足其要求的类型；复杂类对象通常应保护整个操作，而不是只保护其中一个指针成员。

## 八、实践建议

- 在初始化列表中直接初始化成员，特别是引用、`const` 和不可默认构造的类型。
- 根据复制、移动和赋值的语义分别设计资源所有权，不要依赖隐式生成的特殊成员函数处理裸资源。
- 为自定义赋值运算符写清自我赋值、异常安全和移动后的状态保证。
- 将汇编用于验证具体编译配置，不用它替代 C++ 对象模型和内存模型。
- 跨线程发布对象时，先建立明确的同步协议，再讨论底层指令是否“看起来是原子的”。
